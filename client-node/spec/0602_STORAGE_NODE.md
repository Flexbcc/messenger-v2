# 0602. Storage node

## Статус
Черновик

## Назначение
Узел, отвечающий за временное хранение сообщений для офлайн-получателей
(Storage Node, [[0004_GLOSSARY]]). Используется только тогда, когда
получатель временно недоступен.

## Ответственности
- Буферизация зашифрованных Packet, адресованных недоступному получателю, до его повторного подключения.
- Удаление Packet после подтверждённой доставки или истечения срока хранения.

Storage Node **не расшифровывает** и не может расшифровать содержимое —
хранит исключительно E2EE-шифротекст (Privacy First, Single
Responsibility) и **не участвует** в принятии решений о маршрутизации.

## Политики хранения (retention)
Референсная политика: Packet хранится до подтверждённой доставки, но не
дольше фиксированного периода (например, 30 дней) — после истечения срока
недоставленный Packet удаляется безвозвратно. Конкретное значение TTL —
параметр развёртывания конкретного Storage Node, а не требование
протокола.

## Шифрование хранимых данных
Storage Node хранит только шифротекст, полученный по сети — у него нет и
не может быть ключа для его расшифровки (см. [0300_CRYPTO.md](0300_CRYPTO.md)
→ Шифрование хранимых данных). Дополнительно применяется шифрование на
уровне диска/тома как защита в глубину.

## Взаимодействие с базой данных / S3
Метаданные буфера (какому получателю адресован Packet, отметка времени,
TTL) хранятся в базе данных (см. [0700_DATABASE.md](0700_DATABASE.md)).
Крупные вложения через Storage Node не проходят — они обслуживаются
отдельно Media Node и S3-совместимым хранилищем (см.
[0701_S3.md](0701_S3.md)).

## Масштабирование и репликация
Storage Node шардируется по ассоциированной Home Node получателя и
реплицируется для устойчивости к отказу отдельного узла хранения —
поскольку данные уже зашифрованы end-to-end, репликация не увеличивает
поверхность утечки содержимого сообщений.
