# 0604. Discovery node

## Статус
Черновик

## Назначение
Узел, обеспечивающий обнаружение пиров и разрешение идентификаторов
пользователей в адреса их Home Node (Discovery Node,
[[0004_GLOSSARY]]). Discovery Node не участвует в доставке сообщений
(Single Responsibility).

## Ответственности
- Разрешение `UserID → Home Node address` по запросу.
- Публикация каталога Capability других узлов сети (какие Relay/Storage/Media/Discovery узлы существуют и доступны).
- **Control Plane сети** (см. [ADR-0009](ADR/0009-node-enrollment.md)): регистрация нод, жизненный цикл доверия (`trust_status`), мониторинг heartbeat, публичный каталог только для `trusted` нод.
- На bootstrap-стадии проекта (см. [ADR-0006](ADR/0006-staged-decentralization-bootstrap-authority.md)) — приём регистрации и heartbeat от узлов сети, вычисление их статуса online/offline и заявленной версии ПО.

Discovery Node **не участвует** в маршрутизации и доставке сообщений
(data plane). Federation Home↔Home и Relay fallback остаются между
участниками data plane.

## Trust lifecycle (Control Plane)
Каждая нода в реестре имеет `trust_status`:

| Статус | Смысл |
|--------|-------|
| `pending` | Зарегистрировалась, ожидает подтверждения оператором |
| `trusted` | Одобрена, видна в публичном каталоге |
| `suspended` | Временно отозвана оператором |
| `compromised` | Помечена как скомпрометированная |
| `unknown` | Legacy / не классифицирована (миграция) |

Доступность (`reachability`: `online`/`offline`) вычисляется отдельно по
давности heartbeat (порог 120 с). Поле `status` в API — alias для
`reachability` (обратная совместимость).

Режим `ENROLLMENT_MODE=legacy` (по умолчанию) сохраняет прежнее поведение:
регистрация сразу даёт `trusted`. Режим `strict` включает полный enrollment
(ADR-0009).

## Регистрация узлов, heartbeat и статус (bootstrap-стадия)
Каждый Node (Home/Relay/Storage/Media) при старте регистрирует свой
`node_id`, `node_url`, список Capability и `software_version` в корневом
Discovery Node, а затем периодически отправляет heartbeat. Discovery Node
считает Node офлайн, если heartbeat не приходил дольше порогового времени
(референс: 120 секунд). Это единственная форма проверки состояния сети
на данном этапе — не путать с проверкой содержимого сообщений: Discovery
Node по-прежнему не участвует в доставке и не видит содержимое Message.

Результат виден оператору сети через простую read-only панель (Node
Monitor), а не встроен в клиентский UX — это инструмент эксплуатации
сети, а не часть протокола, которым пользуется Client.

Как явно зафиксировано в [ADR-0006](ADR/0006-staged-decentralization-bootstrap-authority.md),
это временный, операционный центр на bootstrap-стадии проекта, а не
постоянное архитектурное требование — со временем предполагается переход
к нескольким Discovery Node и взаимной сертификации узлов без единого
корня.

## Модель адресации
Каждый пользователь адресуется стабильным идентификатором, производным от
его публичного Identity-ключа, а не от email/телефона конкретного
провайдера — это позволяет разрешать адрес независимо от того, какой
оператор инфраструктуры обслуживает Home Node пользователя в данный
момент (Decentralization First).

## Приватность обнаружения
Discovery Node по своей роли неизбежно видит, кто кого пытается найти —
это худший с точки зрения приватности узел сети с точки зрения
социального графа. Минимизация этого риска: rate limiting запросов,
отсутствие возможности массового перечисления пользователей (enumeration),
и рассмотрение техник приватного пересечения множеств (private set
intersection) для обнаружения контактов как направление будущей работы, а
не требование первой версии.

## Кэширование результатов discovery
Client кэширует результат разрешения адреса с ограниченным TTL и
проверяет подпись записи самостоятельно (Zero Trust) — это снижает
нагрузку на Discovery Node и уменьшает объём данных о частоте обращений,
которые Discovery Node может собрать за единицу времени.

## Отказоустойчивость и репликация
Discovery-записи реплицируются между несколькими независимыми Discovery
Node (референс: gossip-репликация подписанных записей, аналогично
распределённому реестру записей без единого источника истины) — потеря
одного Discovery Node не должна делать пользователей ненаходимыми, пока
хотя бы одна реплика записи доступна.
