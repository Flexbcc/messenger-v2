# Как это устроено

Разбор для оператора: что за сервисы, кто за что отвечает, что с чем
разговаривает. Без терминов, которые ничего не объясняют.

---

## Коротко

Мессенджер устроен как **федерация**: нет одного главного сервера, есть
много независимых нод. У каждого пользователя есть «домашняя» нода — та,
где лежит его аккаунт. Ноды договариваются между собой напрямую.

Аналогия — электронная почта. У тебя ящик на одном сервере, у собеседника
на другом, но письма ходят. Никто не владеет «всей почтой».

```
   Аня                                              Боря
    │                                                 │
    ▼                                                 ▼
┌─────────┐        сообщение идёт            ┌─────────────┐
│  нода   │ ────── напрямую между ────────▶  │    нода     │
│  Ани    │          нодами                  │    Бори     │
└─────────┘                                  └─────────────┘
     │                                              │
     └──────────► Discovery ◄─────────────────────-─┘
              «а где живёт Боря?»
```

## Сервисы

### Home-node — сердце

Хранит аккаунты, устройства, чаты и сообщения. К нему подключается
приложение. Это **API, а не сайт** — открыв его в браузере, ты увидишь
страницу состояния, но пользоваться мессенджером оттуда нельзя.

| | |
|---|---|
| Порт | 8001 |
| Хранит | пользователей, устройства, сообщения (зашифрованные) |
| С кем говорит | discovery, storage, media, другие home-ноды |

Сообщения зашифрованы на устройствах. Нода видит зашифрованный текст и
метаданные (кто кому, когда) — прочесть содержимое не может.

### Discovery — справочная

Отвечает на вопрос «на какой ноде живёт этот пользователь». Хранит реестр
нод: кто в федерации, кто онлайн, какой у кого уровень доверия.

| | |
|---|---|
| Порт | 8003 |
| Хранит | список нод, метрики из heartbeat, журнал админ-действий |
| Не хранит | сообщения, ключи, содержимое переписки |

Каждая нода раз в интервал шлёт сюда heartbeat: «я жива, вот моя загрузка».
Отсюда админка берёт CPU, RAM и прочее — не опрашивая ноды напрямую.

### Storage-node — буфер

Если получатель офлайн, сообщение кладётся сюда и ждёт. Как ячейка
хранения: зашифрованный свёрток лежит, пока не заберут.

| | |
|---|---|
| Порт | 8002 (внутренний, наружу не торчит) |
| Хранит | недоставленные сообщения |

### Media-node — файлы

Фото, голосовые, документы. Тоже зашифрованные — нода хранит набор байт,
не зная, что внутри.

| | |
|---|---|
| Порт | 8004 |

### Relay-node — обходной путь

Когда две ноды не могут связаться напрямую (NAT, файрвол), сообщение идёт
через relay. Он передаёт зашифрованный свёрток дальше, не заглядывая внутрь.

| | |
|---|---|
| Порт | 8005 (внутренний) |

### TURN-node — для звонков

Помогает установить связь для аудио и видео, когда прямое соединение не
получается. Сам разговор через него не идёт, он только помогает соединиться.

| | |
|---|---|
| Порт | 8006 |

### Push-proxy — уведомления

Отправляет пуши на телефоны через сервисы Apple и Google. Вынесен
отдельно, чтобы ноды не хранили ключи от этих сервисов.

| | |
|---|---|
| Порт | 8008 (внутренний) |

## Что такое площадка (CLUSTER_ID)

**Площадка — это один оператор со своим набором нод.**

Ты держишь home + media + storage — это одна площадка. Твой знакомый
поднял свои ноды — это другая площадка. Обе в одной федерации, но
хозяйства разные.

`CLUSTER_ID` — имя площадки. Все ноды одного оператора носят одинаковый,
и панель группирует их в одну строку.

В тестовом стенде площадки такие:

| CLUSTER_ID | Что внутри | Изображает |
|---|---|---|
| `core` | home, media, storage, relay, turn | твой сервер |
| `client-1` | home, media, storage | чужая нода №1 |
| `client-2` | home, media, storage | чужая нода №2 |
| `client-3` | home, media, storage | чужая нода №3 |

Так один Docker изображает четырёх независимых операторов.

## Настройка «Адрес для клиентов»

Та самая, которая вызвала вопрос. Отвечает на: **какой адрес приложение
должно использовать, чтобы достучаться до ноды.**

Проблема в том, что у ноды адресов несколько:

| Откуда смотрим | Адрес |
|---|---|
| Изнутри Docker | `msng-core-home:8001` |
| С этого компьютера | `localhost:8001` |
| Из локальной сети | `192.168.1.50:8001` |
| Из интернета | `mynode.example.com` |

Нода не может угадать, какой из них правильный — это зависит от того,
откуда придут пользователи. Поэтому адрес задаётся вручную и уходит
в discovery: когда чужая нода спросит «куда слать сообщения для этого
пользователя», ей ответят именно этим адресом.

Отсюда следствие: **если указать `localhost`, снаружи достучаться не
смогут**. Для локального теста это нормально — всё на одной машине.

### Почему это в админке

Потому что это решение оператора, а не разработчика. Переехал на другой
сервер, купил домен, сменил порт — адрес меняется, и это нормальная
эксплуатационная задача, а не повод пересобирать образ.

---

## Про домен и DNS

Их отсутствие сейчас **не мешает** — просто ограничивает.

| | Без домена (сейчас) | С доменом |
|---|---|---|
| Адрес ноды | `localhost:8001` | `node.example.com` |
| Шифрование канала | самоподписанный сертификат | настоящий TLS |
| Доступ снаружи | только с этой машины | откуда угодно |
| Смена сервера | новый адрес у всех | домен остаётся |

Для проверки логики федерации домен не нужен: ноды находят друг друга
через discovery по тем адресам, что записаны в реестре. Docker создаёт
внутреннюю сеть, где имена контейнеров работают как DNS — `msng-core-home`
резолвится сам.

Домен понадобится, когда ноды разъедутся по разным машинам.

## Что можно проверить сейчас, а что нет

### Работает в Docker

- Регистрация и вход
- Переписка между пользователями **разных** нод — главное в федерации
- Доставка офлайн-получателю через storage
- Передача файлов
- Обходной путь через relay
- Реестр: приём нод, уровни доверия, отключение
- Телеметрия и журнал действий

### Требует отдельных машин

- Реальные сетевые задержки — сейчас всё в одной сети
- NAT и файрволы — в Docker их нет, relay не проверить по-настоящему
- Настоящий TLS с валидным сертификатом
- Поведение при обрыве связи между площадками
- Нагрузка — четыре ноды на одном ноутбуке делят ресурсы

Про десять виртуалок мысль верная, но не первым шагом. Сначала логика
в Docker, потом железо.

## Как проверить, что всё живо

```bash
cd msng-test
./diag.sh        # состояние контейнеров, порты, логи упавших
./health.sh      # отвечают ли ноды
```

Или в браузере:

| Что | Адрес |
|---|---|
| Панель управления | http://127.0.0.1:9310 |
| Главная нода | http://localhost:8001 |
| Клиентская нода 1 | http://localhost:8011 |
| Клиентская нода 2 | http://localhost:8022 |
| Клиентская нода 3 | http://localhost:8031 |
| Реестр федерации | http://localhost:8103/registry/nodes |

Открыв ноду, увидишь страницу состояния: имя, площадка, адрес для
клиентов, сколько человек онлайн. Это не веб-интерфейс мессенджера —
им пользуются из приложения.

## Как проверить главное — переписку между нодами

Смысл федерации в том, что пользователи **разных** нод переписываются.
Проверяется так:

1. Собрать веб-клиент: `./build-web.sh`
2. Открыть http://localhost:3000, зарегистрироваться, указав ноду
   `http://localhost:8001` (площадка core)
3. Открыть второе окно в режиме инкогнито, зарегистрироваться на
   `http://localhost:8011` (площадка client-1)
4. Написать друг другу

Если сообщения дошли — федерация работает: два независимых оператора
обменялись данными через discovery, ни один не был посредником для
содержимого.

## Кто с кем разговаривает

```
                    ┌──────────────┐
                    │  Discovery   │  «кто где живёт»
                    └──────┬───────┘
                           │ heartbeat + запросы
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   ┌─────────┐        ┌─────────┐        ┌─────────┐
   │  core   │◀──────▶│client-1 │◀──────▶│client-2 │
   │  home   │ сообщения напрямую        │  home   │
   └────┬────┘        └────┬────┘        └─────────┘
        │                  │
   ┌────┴────┐        ┌────┴────┐
   │ storage │        │ storage │   буфер для офлайна
   │  media  │        │  media  │   файлы
   └─────────┘        └─────────┘

   ┌─────────┐
   │  relay  │  обходной путь, если напрямую не вышло
   └─────────┘
```

Discovery участвует только в поиске. Сами сообщения через него не идут —
он не узнает, кто кому написал.

## Управление

Панель запускается **на машине оператора**, а не на сервере. На серверах
её нет вообще — так до неё нельзя достучаться из интернета.

| Где | Как | Защита |
|---|---|---|
| Локально | http://127.0.0.1:9310 | порт привязан к 127.0.0.1 |
| Удалённый сервер | пульт из `operator-console/` | клиентский сертификат |

У клиентских нод своей панели нет — они управляются своими владельцами.

Подробности про доступ к удалённым нодам — в `msng-test/README.md`.
