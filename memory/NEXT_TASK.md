# NEXT_TASK

Шаги 1–4 звонков сделаны (см. CURRENT_STATE): сигналинг-плейсинг, методы
`AppController`, `services/turn-node/`, интеграция `flutter_webrtc` (реальный
`RTCPeerConnection`, offer/answer/ICE, устойчивость к сети —
`waitingForNetwork`/`restartIce`/таймаут 20с перед реальным завершением).
Дальше по одному шагу:

1. **UI: подключить `calls_screen.dart` и in-call/incoming-call экраны к
   `AppController.currentCall`.** Это единственное, чего не хватает для
   реального сквозного звонка между двумя пользователями — сама логика
   (`startCall/answerCall/rejectCall/cancelCall/endCall`, ICE, устойчивость
   к сети) готова и живёт в `AppController`/`CallMediaController`, но её
   не с чем вызвать: ни кнопки начать звонок (например, в `chat_screen.dart`
   для 1:1-переписки), ни экрана входящего звонка, ни экрана текущего
   звонка (с индикатором «ожидание сети» из `currentCall.waitingForNetwork`,
   локальным/удалённым видео через `RTCVideoView` для видеозвонков).
   **Это же единственный способ реально проверить звонок целиком** —
   `flutter_webrtc` не работает под `flutter test` (нужен настоящий браузер/
   устройство с платформенными каналами), и пока нет UI-кнопки, вызвать
   `startCall` не через код нельзя. Два браузерных таба уже настроены для
   этого (`messenger-web`/`messenger-web-user2`, `.claude/launch.json`,
   разные порты 9100/9101 → разные origin → разные identity, в одном табе
   через `flutter test` два `AppController` идентичность делят, см.
   ограничение в CURRENT_STATE).
2. Реальный coturn-процесс (или альтернатива) рядом с `turn-node`,
   настроенный на тот же `TURN_SHARED_SECRET` — задача деплоя, см.
   `services/turn-node/README.md`. Не блокирует пункт 1 (можно
   разрабатывать/проверять на STUN-only, TURN нужен только для
   NAT/firewall-заблокированных сетей).

Другие кандидаты, отложенные ранее:
- Android-сборка — проверить SDK/permissions/cleartext HTTP.
- Настройки — оставшиеся заглушки: Аккаунт/Оформление/Помощь/О приложении (сейчас snackbar).
- Private Mode — реальное шифрование хранилища скрытых чатов — требует отдельного security review перед стартом (см. spec/0402 → Требования к реализации), не начинать без явного отдельного решения.

Известное ограничение группового E2EE (MVP): нет добавления/удаления участников после создания группы, нет ротации sender key при выходе — см. spec/0301 → компромиссы.
