# Live Simulation / Живая сеть (Этап 1)

> Статус: **работающая визуальная модель**. Реальная крипта/WebRTC/сокеты не
> используются; структура данных и события приближены к будущей архитектуре.

## Зачем

Пошаговые сценарии объясняют, **как** сеть пришла к состоянию (причинно-
следственная цепочка). Live Mode показывает, **как сеть живёт постоянно**: общение,
файлы, синхронизация, смена маршрутов, очереди, нагрузка, сбои и авто-восстановление.

Переключатель в верхней панели визуализатора: **Сценарий / Живая сеть**. Оба режима
делят одну event-sourcing модель (общие сущности `objects`, типы событий, редьюсер
мутаций из `sim/engine.js`).

## Архитектура (event loop, §20)

```
Simulation clock → Event generator → Routing decision → State mutation
→ Resource aggregation → Snapshot → Render
```

Разделение слоёв:
- `sim/rng.js` — **seeded** ГПСЧ (mulberry32). Один seed → одинаковое поведение.
- `sim/presets.js` — топология сети (агенты/инфраструктура) + 6 presets нагрузки.
- `sim/routing.js` — **routing decision engine**: из текущего состояния выбирает
  `DIRECT | RELAY | HOME_STORAGE | S3_FALLBACK | LOCAL_QUEUE | WAITING` + объяснение.
- `sim/liveEngine.js` — `LiveEngine`: держит мир, на каждый `tick()` прогоняет
  генератор, прогресс передач, изменения сети, ресурсы; ведёт статистику и журнал
  (cap 1000). Снимок для рендера — `snapshot()`.
- `components/network/LiveSim.jsx` — UI: presets, Play/Pause/Step/Reset, скорость
  0.25–10x, seed (replay/new), дашборд, журнал с фильтрами, ресурс-панель, инспектор.
- `NetworkCanvas.jsx` — рендер множественных маркеров передач (иконки по типу).

Бизнес-логика **не** привязана к SVG: движок мутирует состояние, компонент рисует
снимок. Рендер ~7 fps, накопитель тиков масштабируется скоростью.

## Presets (§17)

`calm · normal · busy · unstable · threat · family` — различаются вероятностями на
тик: messageRate, mediaRate, fileRate, syncRate, offlineProb, routeFailProb,
attackProb, loadSpikeProb, callProb.

## Live-события

Тексты, фото/видео/файлы (с индикатором %), синхронизация (телефон→Home), звонки
(signalling→media), атаки (scan/replay/route-revocation). Сетевые изменения: узлы
уходят/возвращаются online, прямой маршрут теряется/восстанавливается, всплеск
личной нагрузки. Ресурсы: личная нагрузка вытесняет community (preemption),
состояние Home меняется NORMAL→BUSY→OVERLOADED→CRITICAL по CPU.

## Типы объектов

Пользователи (Alice/Bob/Carol), устройства (phone/laptop), OUO Home A/B, relay-1/2,
witness, discovery, S3-A/B, net. Форма объектов та же, что в сценариях → общий
рендер, инспектор и ресурс-панель.

## Resumable transfers

Если узел на пути уходит offline, передача не начинается заново: маршрут
пересчитывается, прогресс сохраняется (продолжение с текущего %).

## Агрегация (§22–23)

Одновременно рисуется не более ~9 передач; остальные сворачиваются в счётчик
`(+N)`. Журнал фильтруется по категориям: Текст/Медиа/Синхр./Звонки/Помощь
сети/Безопасность.

## Статистика (§25)

Сообщения (created/delivered/waiting), Медиа (uploaded/downloaded/replicated),
Маршруты (direct/relay/S3/queue), Безопасность (сканы/повторы/отзывы/звонки).
Header: время симуляции, события, активные передачи, доставлено, seed.

## Проверено (критерии §28)

Все 15 пунктов: запуск, непрерывное общение, тексты, фото/файлы, direct/relay/S3/
queue, Home offline→fallback→recovery, вытеснение community, очереди, смена
маршрута без ручного шага, Pause, один tick, replay по seed (детерминизм
подтверждён: одинаковый seed → идентичная последовательность), RU/EN, мобильная
ширина без переполнения.

## Масштаб и скриптуемость (30–40 пользователей)

Мир больше не хардкодится (3 фиксированных пользователя) — `sim/presets.js` строит
**топологию произвольного размера**: пользователи размещаются по кольцу вокруг
инфраструктуры (discovery/witness/relay×N/S3×N), у части — собственный OUO Home
(своё хранилище), у остальных — только устройство, полагающееся на relay/S3
fallback. Размер сети переключается кнопками **8/14/22/30/40** в тулбаре
(«Пересобрать» применяет новый размер к текущему seed/preset).

`routing.js` и `liveEngine.js` полностью общие по числу узлов — `usableRelays`/
`usableStorage` сканируют объекты по `kind`, а не по фиксированным id; ресурсы,
offline-события и атаки выбирают случайную ноду из динамических списков
`relayIds`/`homeIds`.

**Сеть управляется как скрипт** — вкладка **Консоль** в правой панели:
кнопки быстрых действий (+ пользователь с/без Home, + relay/S3-нода, отключить
случайный relay/Home, заблокировать случайную пару, снять все блокировки,
восстановить все ноды) и текстовые команды:

```
add user [home|nohome]
add node [relay|s3]
revoke <deviceId>
block <a> <b>
unblock <a>|<b>   |   unblock all
kill <id>
revive <id>
```

Все команды — публичные методы `LiveEngine` (`addUser`, `addNode`, `revokeDevice`,
`blockPair`/`unblockPair`, `killNode`/`reviveNode`), вызываемые одинаково из
кнопок и из парсера команд — один и тот же API. Каждое действие пишет запись в
журнал живой сети.

Вкладка **Участники** — прокручиваемый список всех пользователей с индикатором
🏡 (свой Home) / 📱 (только устройство) и online-точкой; клик выделяет узел на
canvas и открывает его карточку в Инспекторе. Это и есть ответ на «кто имеет
своё хранилище, а у кого его нет» при 30–40 пользователях, когда canvas сам по
себе становится плотным.

Иконки на canvas адаптивно уменьшаются при росте сети (`iconScale`): подписи и
мини-полоски CPU/RAM скрываются при size ≥22, чтобы кольцо из 40+ узлов
оставалось читаемым.

Проверено: 40 пользователей → 79 объектов на canvas, симуляция стабильна на
скорости 10x (2:50 симуляционного времени за ~4.6 с реального, 138/144
сообщений доставлено), добавление пользователя/ноды, блокировка пары,
kill-ноды — каждое действие немедленно отражается в топологии, ресурсах и
журнале; сеть продолжает маршрутизировать в обход заблокированных/убитых узлов.

## Теоретическая задержка (мс) по типу сообщения и маршруту

Новая вкладка **«Задержка»** в правой панели (доступна и в Scenario, и в Live
Mode) — `sim/latency.js`: справочная таблица теоретической задержки доставки
(мс) для каждой комбинации тип сообщения (text/photo/video/file/sync/call/ack)
× маршрут (DIRECT/RELAY/HOME_STORAGE/S3_FALLBACK/LOCAL_QUEUE). Значения —
порядок величины (клиентский оверхед шифрования + задержка транспорта за хоп +
надбавка маршрута, например HTTPS upload/download для S3), не измерение
реальной сети — явно помечено в подсказке над таблицей. Наведение на ячейку
показывает диапазон min–max.

`routing.js` подставляет `etaMs` в каждое решение `decideRoute()` (детерминированный
джиттер через `world.rng`, чтобы значение не было оторвано от выбора маршрута).
В Live Mode это же число: попадает в лог доставки (`~111 мс`) и накапливается в
`stats.latencyByRoute`/`latencyByKind` — под справочной таблицей появляется блок
«Среднее по текущей симуляции» с фактическими средними по мере работы сети.

## Ограничения / что осталось моделью

- `waiting` — кумулятивный счётчик ушедших в очередь (не «сейчас в очереди»):
  отдельных persistent-объектов очереди пока нет.
- Групповой чат, отдельные device-ключи, полноценные звонки (media pulse),
  репликация как отдельные объекты — Этап 2/3.
- Реальная крипта/NAT traversal/сокеты — симулируются.
