# Update security

> Статус: **модель**.

## Процесс безопасного обновления

```
1. Проверка подписанного update manifest
2. Проверка версии и платформы
3. Скачивание пакета
4. Проверка hash
5. Проверка цифровой подписи
6. Подготовка rollback
7. Установка
8. Перезапуск
9. Health check
10. Автоматический откат при неудаче
```

## Требования

- подписанные обновления;
- защита от downgrade;
- несколько каналов обновления (стабильный и тестовый);
- журнал обновлений;
- аварийный откат;
- отсутствие единственного небезопасного URL обновлений;
- прозрачная версия компонентов.

Update Service изолирован и **не** имеет доступа к пользовательским данным (см.
[threat-model](threat-model.md) §изоляция).

## Реализовано в визуализаторе

Сценарий «Уязвимость Relay → обновление» показывает: скачивание пакета, проверку
hash и подписи, подготовку rollback, установку 2.3.1, защиту от downgrade, health
check и авто-откат при неудаче.

## Открытые вопросы

- Инфраструктура подписи и ротация ключей подписи обновлений.
- Механика тестового канала и постепенного раскатывания.
