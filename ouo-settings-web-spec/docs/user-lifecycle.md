# User & Device Lifecycle / Жизненный цикл пользователя и устройств

> Статус: **работающая визуальная модель**. Реальная крипта (Ed25519/X3DH/Double
> Ratchet), QR-протокол и сетевые вызовы не реализованы; структура событий
> приближена к будущей архитектуре.

## Зачем

Разделы «Сеть OUO» и «Безопасность OUO Home» объясняют, как сеть строится и как
она защищается. Эта сцена закрывает третий вопрос: **что происходит с самим
пользователем и его устройствами** — от первого запуска до потери устройства и
ротации ключей (§26 A/G/H/I исходного ТЗ).

Третья категория в переключателе сценариев: **Сеть OUO / Безопасность OUO Home /
Жизненный цикл пользователя**. Использует ту же event-sourcing модель
(`sim/engine.js`, общие `objects`/`EVENT_TYPE`) — новый движок не создавался.

## Сценарии

| # | Сценарий | Показывает |
|---|---|---|
| 1 | Первый запуск: от установки до первого сообщения | установка клиента → локальная identity → device key → выбор режима сети → установка OUO Home → выбор диска и лимита → регистрация в discovery → pairing по QR (с уничтожением token) → добавление контакта по QR → первое сообщение + ACK |
| 2 | Второе устройство: независимые ключи | новый QR для ноутбука → **собственный** device key (не общий с телефоном) → fan-out доставка: одно сообщение независимо расшифровывается и телефоном, и ноутбуком |
| 3 | Потеря и отзыв устройства | устройство потеряно → отзыв ключа с доверенного устройства → обновлённый список устройств → новые сообщения не шифруются для отозванного устройства → честная оговорка: **данные, уже сохранённые на потерянном устройстве, удалённо не стираются** |
| 4 | Ротация ключей | плановая ротация identity-ключа, ключа ноды и device key → контакт предупреждён об изменении → требуется повторная верификация → fingerprint сверен → доверие восстановлено |
| 5 | Восстановление Home Node и миграция на NAS (§26 J/K) | отказ диска → данные на устройствах не пострадали → найден зашифрованный backup → новая Home регистрируется в discovery → backup расшифрован своим паролем → недостающее дозагружено из копии у друга → устройства подтверждают fingerprint новой ноды → позже: перенос на NAS, копирование object store, сверка hash, переключение endpoint, старая нода выведена из реестра |

## Ключевая идея

Identity, device key и node key — **три разные сущности**, которые не совпадают и
не передаются между устройствами. Устройство не разделяет приватный ключ с другими
устройствами того же пользователя: у каждого — своя пара ключей, полученная через
отдельный pairing. Это видно в сценарии 2 (двойная независимая расшифровка) и в
инспекторе объекта устройства (поле «Ключ устройства»).

QR-пейринг — одноразовый и короткоживущий: объект QR добавляется на канвас и
**удаляется** после использования (новая мутация `remove` в `sim/engine.js`,
аддитивно расширяющая редьюсер — старые сценарии её не используют и не затронуты).

## Честность модели

Сценарий 3 намеренно не показывает «магическое» решение: отзыв ключа устройства
останавливает *будущее* шифрование для него, но не имеет технической возможности
стереть то, что уже было расшифровано и сохранено на потерянном устройстве. Это
согласуется с ограничением E2EE, зафиксированным в
[threat-model.md](threat-model.md) (сценарий C: скомпрометированное устройство).

## Не реализовано (модель, не код)

Настоящая генерация ключей и QR-кодов, реальный протокол взаимной аутентификации
устройств, синхронизация истории между устройствами без передачи общего ключа
(только заявлена, не смоделирована на уровне данных), поиск пользователя через
несколько нод без глобального реестра (частично показано в сценарии 1 через QR +
route hint, полноценно — отдельная тема).
