# Локальный деплой на несколько машин (домашняя лаба)

Под топологию: 1 ПК с 4 виртуалками (по одной ноде на VM) + отдельный ПК
как главная нода (discovery + мониторинг). Все машины в одной локалке.

## Требования на каждой машине
- Docker + Docker Compose (`docker --version`, `docker compose version`).
- Порт, который эта нода слушает, открыт в локалке (обычно достаточно, что
  все машины в одной подсети — доп. настройка файрвола не нужна).

## Шаги

1. На **каждой** машине (главный ПК + 4 VM) — склонировать репозиторий.
2. На главном ПК:
   ```
   ./scripts/setup-node.sh
   ```
   Выбрать `1) discovery`, ввести LAN IP этого ПК. Поднимется только
   discovery-node (порт 8003).

   Дальше на этом же ПК (или на любой другой машине в сети, если хочется
   смотреть панель не с самой discovery-машины) — второй раз:
   ```
   ./scripts/setup-node.sh
   ```
   Выбрать `7) admin`. Откроется `http://<IP этой машины>:9200` — в поле
   "Discovery Node URL" вписать `http://<IP главного ПК>:8003`.

3. На каждой из 4 VM — по одной роли:
   ```
   ./scripts/setup-node.sh
   ```
   Выбрать `2) home`, `3) storage`, `4) media` или `5) relay` — по одной
   на VM. Скрипт спросит IP этой VM и IP discovery — впишите LAN IP
   главного ПК из шага 2. Для роли `home` дополнительно спросит IP VM с
   `storage`.

4. Открыть admin-панель (шаг 2) — через 5-10с все 4+1 нод должны
   появиться со статусом `online`, реальным пингом и нагрузкой.

## Как это работает "само"
- Каждая нода при старте регистрируется в discovery и раз в 60с шлёт
  heartbeat. Если discovery в момент старта ещё не поднялась (машины не
  обязаны стартовать в одном порядке) — нода не падает и не бросает
  попытки, а ретраит с экспоненциальной паузой (2с→4с→…→30с), пока
  discovery не ответит. Живьём проверено: поднял всё, кроме discovery,
  подождал — все ушли в ретраи; поднял discovery — все сами
  зарегистрировались без перезапуска.
- Если discovery-node пришлось поднять с нуля (потеряла БД) — остальные
  ноды это тоже переживут: при следующем heartbeat получат 404 и
  перерегистрируются автоматически, а не будут долбить в пустоту.

## Проверка, что всё реально работает (не только "статус online")
`admin/` показывает пинг и нагрузку по каждой роли — это НЕ просто
"процесс жив", а честная проверка: pинг — реальный RTT из браузера до
`/health` ноды; нагрузка — активные WS/переслано пакетов/буфер/файлы,
т.е. видно, что нода реально что-то делает, а не просто отвечает на
health-check.

Дальше, если нужно проверить полный путь сообщения (регистрация →
переписка → доставка), можно руками прогнать HTTP-запросы к home-node
(`/auth/register`, `/conversations`, `/conversations/{id}/messages`) с
разных VM — если home и получатель на разных home-node, сработает
федерация (прямая доставка → relay fallback), это уже проверялось в
рамках текущей сессии на одной машине с искусственными задержками.

## Известные ограничения этого шага
- `docker-compose.yml` не поднимает TLS — трафик между нодами внутри
  локалки идёт по HTTP. Для лабы это нормально, для чего-то за пределами
  доверенной локалки — нет.
- `admin/`, все `/health`-эндпоинты и `TURN_SHARED_SECRET` по умолчанию —
  без аутентификации. Не выставлять эти порты за пределы локалки.
- SQLite-файлы каждой ноды лежат в `./data/<нода>/` рядом с
  `docker-compose.yml` — бэкапить/переносить нужно руками, репликации
  между нодами нет (см. `spec/0700_DATABASE.md`).
