# 0002. Принципы

## Статус
Черновик

## Назначение
Инженерные и продуктовые принципы, которыми руководствуется команда при
принятии решений. Каждый принцип должен помогать разрешать споры и
конфликтующие компромиссы. Принципы перечислены в порядке изложения; Privacy
First и Decentralization First являются фундаментальными и упоминаются как
основа всех остальных решений.

## Принципы

### 1. Privacy First
Конфиденциальность — один из фундаментальных принципов проекта.

- Ни один сетевой узел не должен получать больше информации, чем необходимо для выполнения своей задачи.
- Содержимое сообщений всегда остаётся доступным только отправителю и получателю.
- Все криптографические механизмы используют проверенные и общепринятые алгоритмы. Проект не разрабатывает собственные криптографические примитивы.

См. [0300_CRYPTO.md](0300_CRYPTO.md).

### 2. Decentralization First
Система не должна иметь единой точки отказа.

> На текущей bootstrap-стадии проекта действует осознанное временное
> отступление от этого принципа — см. [ADR-0006](ADR/0006-staged-decentralization-bootstrap-authority.md):
> один корневой Discovery Node используется для регистрации и мониторинга
> остальных нод, с явным roadmap на децентрализацию этого механизма.

- Любой пользователь может запустить собственный Node.
- Любой пользователь может предоставить инфраструктуру для сети.
- Все основные компоненты должны поддерживать федерацию.
- Работа системы не должна зависеть от существования конкретной компании или организации.

### 3. Offline First
Каждый клиент обязан корректно работать без постоянного подключения к
Интернету.

- Все пользовательские действия сначала сохраняются локально.
- Передача данных происходит автоматически после восстановления соединения.
- Пользователь не должен замечать временную потерю сети.

См. [0400_CLIENT.md](0400_CLIENT.md).

### 4. Modular Architecture
Каждый компонент системы является независимым модулем.

- Любой модуль можно заменить без переписывания остальных компонентов.
- Все взаимодействия осуществляются только через документированные интерфейсы.
- Внутренние реализации не должны влиять на остальные части проекта.

### 5. Replaceable Everything
Проект никогда не должен зависеть от конкретной технологии. Должна
существовать возможность заменить:

- базу данных;
- файловое хранилище;
- транспорт;
- Node;
- Client;
- систему уведомлений;
- механизм хранения файлов;
- облачную инфраструктуру.

Ни одна технология не считается обязательной.

### 6. Protocol Before Framework
Основой проекта является собственная спецификация протокола.

- Реализация является лишь одной из возможных реализаций этой спецификации.
- Любой разработчик должен иметь возможность создать совместимый Client или Node, используя только документацию проекта.

См. [0200_PROTOCOL.md](0200_PROTOCOL.md).

### 7. Community Driven Infrastructure
Любой желающий может подключить собственный Node. Node может выполнять
одну или несколько ролей:

- Home Node ([0600_HOME_NODE.md](0600_HOME_NODE.md));
- Relay Node ([0601_RELAY_NODE.md](0601_RELAY_NODE.md));
- Storage Node ([0602_STORAGE_NODE.md](0602_STORAGE_NODE.md));
- Media Node ([0603_MEDIA_NODE.md](0603_MEDIA_NODE.md));
- Discovery Node ([0604_DISCOVERY_NODE.md](0604_DISCOVERY_NODE.md)).

Все роли независимы друг от друга.

### 8. Federation
Каждый Node является равноправным участником сети.

- Не существует центрального управляющего Node.
- Любой Node может обмениваться сообщениями с другими Node по открытому протоколу.

### 9. Security by Design
Безопасность должна закладываться на этапе проектирования.

- Используются только современные и проверенные криптографические алгоритмы.
- Криптография должна быть полностью отделена от бизнес-логики приложения.
- Каждый уровень системы отвечает только за собственную область безопасности.

### 10. Scalability
Архитектура должна одинаково хорошо работать:

- для двух пользователей;
- для небольшой команды;
- для компании;
- для миллионов пользователей.

Масштабирование не должно требовать изменения архитектуры.

### 11. Extensibility
Мессенджер является только первым приложением платформы. Архитектура должна
позволять создавать дополнительные сервисы:

- голосовые звонки;
- видеозвонки;
- обмен файлами;
- совместную работу;
- AI-модули;
- автоматизацию;
- заметки;
- календарь;
- плагины;
- любые будущие расширения.

## Основная философия разработки
При разработке любого компонента необходимо руководствоваться следующими
вопросами:

- Можно ли заменить этот модуль через несколько лет без переписывания системы?
- Может ли данный компонент работать автономно?
- Можно ли поднять этот компонент самостоятельно?
- Не нарушает ли решение принципы приватности?
- Не появляется ли новая единая точка отказа?
- Можно ли реализовать данный интерфейс на другом языке программирования?
- Останется ли протокол совместимым после будущих изменений?

Если ответ хотя бы на один из этих вопросов отрицательный, архитектурное
решение должно быть пересмотрено.

## Роль искусственного интеллекта
ИИ используется как инженерный помощник. При генерации кода необходимо
соблюдать следующие правила:

- архитектура важнее скорости разработки;
- модульность важнее количества функций;
- читаемость важнее сокращения количества строк кода;
- спецификация имеет приоритет над реализацией;
- документирование является обязательной частью разработки;
- любой новый функционал должен расширять существующую архитектуру, а не обходить её.

ИИ не должен изменять фундаментальные архитектурные принципы без явного
изменения спецификации проекта.

## Приоритеты при конфликте требований
Privacy First и Decentralization First являются основой, на которой строятся
остальные принципы: любое решение, ослабляющее приватность или создающее
новую единую точку отказа, должно быть пересмотрено (см. «Основная
философия разработки» выше). Более детальная иерархия приоритетов между
остальными принципами — TBD, уточняется по мере появления конкретных
архитектурных конфликтов и фиксируется через [ADR](ADR/README.md).
