# 0004. Project Glossary

## Статус
Черновик

## Назначение
Данный документ определяет единый словарь терминов проекта.

Все остальные документы спецификации используют определения только из
данного документа. Запрещается использовать разные названия для одной и той
же сущности. Каждый термин должен иметь одно официальное определение.

Именно эти определения Cloud Code должен использовать всегда.

## Экосистема и участники

### Platform
Вся экосистема проекта. Включает в себя:
- клиентские приложения;
- серверные компоненты;
- сетевые узлы;
- протокол доставки;
- криптографические компоненты;
- SDK;
- API;
- инфраструктуру.

Платформа является более широким понятием, чем мессенджер.

### Client
Приложение пользователя. Клиент предоставляет пользовательский интерфейс.

Клиент отвечает за:
- отображение информации;
- взаимодействие пользователя;
- локальное хранение;
- работу с криптографией;
- синхронизацию.

Клиент никогда не является сервером.

### User
Логическая сущность человека.

Пользователь может владеть несколькими устройствами. Пользователь не
привязан к конкретному устройству.

### Device
Конкретное устройство пользователя. Например: телефон, планшет, компьютер,
ноутбук.

Каждое устройство обладает собственной криптографической идентичностью.

### Identity
Постоянная криптографическая идентичность пользователя или устройства.

Используется для подтверждения подлинности. Identity существует независимо
от подключения к сети.

## Взаимодействие и коммуникация

### Session
Временное состояние взаимодействия между двумя или несколькими
устройствами.

Сессия может быть восстановлена или пересоздана. Сессия не является
пользователем.

### Conversation
Логическая переписка. Может содержать:
- двух участников;
- группу;
- канал;
- будущие типы коммуникации.

Conversation существует независимо от способа доставки сообщений.

### Message
Минимальная единица передачи информации. Сообщение может содержать:
- текст;
- файл;
- изображение;
- видео;
- голосовое сообщение;
- реакцию;
- системное событие.

### Packet
Минимальная единица сетевого протокола.

Packet существует только во время передачи данных. Один Packet может
содержать: сообщение, подтверждение, служебные данные, запрос.

Packet не является сообщением.

## Сетевые узлы

### Node
Любой сетевой узел.

Каждый сервер является Node. Каждый Node выполняет определённую роль.

### Home Node
Основной сервер пользователя.

Может принадлежать: самому пользователю, компании, сообществу.

Home Node отвечает за обслуживание конкретного пользователя.

### Relay Node
Узел доставки.

Relay принимает пакет, определяет следующий маршрут, передаёт пакет дальше.

Relay не читает содержимое сообщений.

### Storage Node
Узел временного хранения.

Используется только тогда, когда получатель временно недоступен. Storage
хранит исключительно зашифрованные данные.

### Media Node
Узел хранения файлов.

Может использовать: локальный диск, MinIO, S3, NAS, облачные сервисы.

Media Node не обязан хранить сообщения.

### Discovery Node
Узел обнаружения.

Используется для поиска других узлов сети. Не участвует в доставке
сообщений.

### Turn Node
Узел ретрансляции медиапотоков звонков.

Используется, когда прямое P2P-соединение между устройствами невозможно
(NAT/firewall). Не участвует в сигналинге звонка и не читает содержимое
медиапотока.

### Federation
Механизм взаимодействия независимых серверов.

Каждый сервер остаётся автономным. Все серверы используют единый протокол.

## Протокол и интерфейсы

### Protocol
Официальная спецификация обмена данными.

Protocol описывает формат пакетов. Protocol не зависит от языка
программирования.

### API
Программный интерфейс взаимодействия компонентов.

API не определяет внутреннюю реализацию.

### SDK
Набор библиотек.

Используется для создания совместимых клиентов и серверов. SDK реализует
Protocol.

## Программные слои и компоненты

### Crypto Layer
Изолированный модуль криптографии.

Crypto Layer отвечает исключительно за:
- генерацию ключей;
- шифрование;
- дешифрование;
- подписи;
- проверку подписей.

Crypto Layer не знает ничего о пользовательском интерфейсе.

### Transport Layer
Модуль доставки данных.

Transport отвечает за: соединения, маршрутизацию, повторную доставку,
подтверждения.

Transport не знает содержимого сообщений.

### Storage Layer
Модуль хранения информации.

Поддерживает различные реализации. Например: SQLite, PostgreSQL, память,
распределённое хранилище.

### Repository
Абстрактный интерфейс доступа к данным.

Позволяет заменить любую реализацию без изменения бизнес-логики.

### Module
Независимый компонент системы.

Каждый Module имеет собственную область ответственности. Модули
взаимодействуют исключительно через публичные интерфейсы.

### Service
Внутренний компонент, реализующий бизнес-логику.

Service может использовать несколько Repository. Service не должен зависеть
от пользовательского интерфейса.

### Event
Описание произошедшего действия. Например: отправлено сообщение,
пользователь подключился, файл загружен.

События используются для слабой связанности компонентов.

### Queue
Очередь обработки.

Используется для: повторной доставки, фоновых задач, синхронизации.

Очередь не является постоянным хранилищем.

### Capability
Описание возможностей узла. Например: Relay, Storage, Media, Discovery.

Каждый Node самостоятельно публикует поддерживаемые возможности.

### Plugin
Расширение платформы.

Плагин не изменяет архитектуру системы. Он использует официальные API и
Protocol.

## Документация и процесс

### Specification
Документация проекта.

Specification имеет более высокий приоритет, чем реализация. Код должен
соответствовать Specification.

### Cloud Code
ИИ-разработчик.

Cloud Code рассматривается как полноценный участник разработки. Он обязан
соблюдать архитектуру проекта. Он не должен принимать решения,
противоречащие Specification.

При возникновении неоднозначности Cloud Code обязан сначала предложить
изменение спецификации, а не самостоятельно менять архитектурные принципы.
