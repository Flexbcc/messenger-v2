# 0402. Private Mode / Secret Room

## Статус
Черновик

## Назначение
Описывает второй, скрытый уровень интерфейса клиента — Private Mode
("Secret Room"): область приложения, доступную только после ввода
отдельного PIN/биометрии, в которой находятся чаты, не видимые в обычном
режиме работы. Источник требований — `screens.md`, поставленный владельцем
продукта; этот документ формализует его в спецификации, прежде чем начинать
даже mock-реализацию (Specification First,
[[0003_ENGINEERING_PRINCIPLES]]).

Это клиентская фича (UI + локальное хранилище), не затрагивающая протокол
или узлы инфраструктуры — Home Node не знает и не должен знать о
существовании Private Mode на клиенте (Privacy by Default: чем меньше
знает сервер, тем лучше).

## Модель угроз и её пределы — читать первым
Прежде чем проектировать конкретные экраны, важно явно ограничить, от чего
эта функция защищает, а от чего — нет. Опыт индустрии (TrueCrypt/VeraCrypt
hidden volumes, аналогичные функции в других мессенджерах) показывает, что
подобные механизмы легко переоценить.

**Защищает от:**
- случайного просмотра телефона знакомым/коллегой, у которого есть обычный доступ к разблокированному устройству;
- поверхностного принуждения показать «свою переписку», когда достаточно правдоподобно показать fake-режим без явных следов существования скрытой части.

**Не защищает от:**
- форензик-анализа устройства или его бэкапа: если скрытые данные лишь отфильтровываются на уровне UI, а физически лежат в той же базе данных, что и обычные, извлечение и анализ файла БД сразу раскрывает их существование. Реальная скрытность требует, чтобы данные Private Mode были зашифрованы ключом, производным от private-mode PIN, так, чтобы зашифрованный блок был неотличим от случайных данных без этого PIN (см. «Требования к реализации» ниже) — это дополнительная работа, выходящая за рамки MVP-версии UI;
- целенаправленного принуждения от того, кто уже знает о существовании подобной функции в принципе (rubber-hose scenario) — ни один программный механизм не может это полностью снять;
- юрисдикций, где отказ раскрыть скрытые данные сам по себе может считаться уликой или правонарушением — это вопрос вне технической реализации.

**Про «удаление при принуждении» (wipe-on-duress).** Эта возможность
рассматривается как опциональная и явно необратимая: она удаляет
пользовательские данные без возможности восстановления и сама по себе
может стать нежелательным сигналом («что-то стиралось»), если противник
уже подозревает Private Mode. Решение о том, включать ли подобный режим
по умолчанию — продуктовое, не техническое, и должно приниматься отдельно,
не в рамках MVP UI-макетов.

## Термины
| Термин | Определение |
|---|---|
| Normal Mode | Обычный режим работы приложения — чаты, звонки, контакты, настройки, видимые по умолчанию. |
| Private Mode / Secret Room | Скрытая область приложения, доступная только после ввода отдельного PIN/биометрии; содержит скрытые Conversation, скрытые контакты, отдельные настройки приватности. |
| Fake PIN / Decoy Mode | Альтернативный PIN, при вводе которого открывается заранее подготовленное «безопасное» состояние приложения без следов существования Private Mode. |
| Panic Exit | Мгновенный выход из Private Mode обратно в Normal Mode по кнопке, жесту или сворачиванию приложения, без визуальных следов. |
| Hidden Conversation | Conversation ([[0004_GLOSSARY]]), помеченная как принадлежащая Private Mode — не отображается в обычном списке чатов, поиске, уведомлениях, истории и медиатеке. |

## Уровни доступа
1. **Normal Mode** — вход по обычной разблокировке устройства/приложения.
2. **Fake PIN** — отдельный PIN, открывающий безопасную предопределённую версию Normal Mode (набор «разрешённых» чатов, без доступа к скрытым).
3. **Private Mode** — отдельный PIN/биометрия, открывающий Secret Room.

Уровни не пересекаются: находясь в Fake PIN режиме, невозможно каким-либо
действием в интерфейсе попасть в Private Mode — это два разных состояния,
активируемых только с экрана разблокировки.

## Что не должно происходить
- Скрытые чаты не должны появляться в обычном списке чатов, глобальном поиске, уведомлениях, галерее медиа или истории ни при каких обстоятельствах, кроме нахождения внутри самого Private Mode.
- Push-уведомления о сообщениях в Hidden Conversation не должны показывать содержимое или сам факт существования такого чата (см. [0202_DELIVERY.md](0202_DELIVERY.md) → доставка офлайн-получателям — та же логика «push как сигнал, не контент» применяется здесь на клиентском уровне).
- Переключение в Fake PIN не должно быть отличимо снаружи от обычного открытия приложения.

## Экраны (mock-уровень MVP)
Полный список и поведение — см. `screens.md`: PIN Setup, Unlock, Fake PIN
Mode, Secret Room, Hidden Chats List, Hidden Chat Dialog, Hide Chat Action,
Privacy Settings, Panic Exit, Device Privacy. Визуально — тот же
минималистичный iOS-style язык из [0401_FLUTTER.md](0401_FLUTTER.md) /
дизайн-системы клиента, без «хакерской» стилизации: Secret Room не должна
выделяться визуально настолько, чтобы её отличие от Normal Mode было само
по себе подозрительным.

## Ограничения этого этапа (MVP)
Как и явно указано в постановке задачи: на этом этапе **не реализуется**
реальная криптография Private Mode — только экраны, моковые данные,
модели состояний и навигация между Normal Mode и Secret Room. Экраны не
должны утверждать (текстом в UI) свойства безопасности, которые ещё не
реализованы по-настоящему — это ввело бы пользователя в заблуждение
(нарушение Privacy First куда более серьёзное, чем отсутствие фичи).

## Требования к реализации (для этапа после MVP UI)
Когда дело дойдёт до реальной криптографии:
- Ключ шифрования локального хранилища Private Mode должен производиться из private-mode PIN через устойчивую к перебору KDF (Argon2id, см. [0300_CRYPTO.md](0300_CRYPTO.md) → Используемые примitives), не переиспользуя ключ основного хранилища приложения.
- Хранилище Hidden Conversation должно быть физически отделено от основной локальной БД (отдельный зашифрованный файл/контейнер), а не логическим фильтром поверх общей таблицы — иначе защита не переживает форензик-анализ файловой системы.
- Fake PIN не должен иметь доступа ни к каким артефактам (файлам, индексам, кэшам), связанным с Private Mode, даже метаданным об их существовании.
- Перед реальной реализацией — независимый security review конкретной схемы хранения (аналогично требованию аудита в [0302_THREAT_MODEL.md](0302_THREAT_MODEL.md)), так как это одна из самых чувствительных к ошибкам частей клиента.
