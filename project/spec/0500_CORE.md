# 0500. Core

## Статус
Черновик

## Назначение
Кроссплатформенная core-логика, общая для всех клиентов: протокол,
криптография, локальное состояние. Core — это Module
([[0004_GLOSSARY]]) с чётко определённой ответственностью, не знающий
ничего о конкретном UI-фреймворке (Single Responsibility, Loose Coupling).

## Ответственности Core
- Реализация протокола ([0200_PROTOCOL.md](0200_PROTOCOL.md) и далее): сборка/разбор Packet, управление Session, handshake.
- Криптографические операции через Crypto Layer ([0300_CRYPTO.md](0300_CRYPTO.md)) — Core вызывает Crypto Layer как отдельный внутренний модуль, а не реализует примитивы инлайн.
- Управление локальным состоянием: очередь исходящих сообщений (Queue), локальный кэш Conversation, дедупликация входящих Packet.
- Сетевое взаимодействие с узлами инфраструктуры (Transport Layer).

Core **не отвечает** за отображение интерфейса, локализацию или
платформенные push-механизмы — это ответственность Client
([0400_CLIENT.md](0400_CLIENT.md)).

## Технологический стек
Референсный выбор — Rust: предсказуемая производительность,
безопасность памяти без сборщика мусора и зрелая экосистема FFI-биндингов
позволяют реализовать Core один раз и переиспользовать из разных
клиентов и языков (Protocol Before Implementation — SDK на разных языках
должны вести себя одинаково, см. [0004_GLOSSARY.md](0004_GLOSSARY.md) →
SDK). Это выбор реализации, а не требование протокола.

## Публичный интерфейс Core → Клиент
Стабильный API (API as Contract), покрывающий как минимум:
- отправка/получение Message в рамках Conversation;
- управление Session и Device (регистрация, отзыв, привязка нового устройства);
- поток Event для реактивного обновления UI (входящее сообщение, изменение статуса доставки, изменение состояния сети) — Client подписывается на Event, а не опрашивает Core (Event Driven, [[0003_ENGINEERING_PRINCIPLES]]).

## Управление жизненным циклом соединений
Core самостоятельно управляет установлением, поддержанием и
восстановлением сетевых соединений с Home Node, скрывая эту сложность от
Client: смена сети, потеря соединения и его восстановление обрабатываются
внутри Core и не должны требовать явного вмешательства UI-слоя (Offline
First).

## Тестирование Core
- Модульные тесты для сборки/разбора Packet и state-машины Session.
- Property-based тесты для инвариантов протокола (например: Packet после сериализации и десериализации идентичен исходному; дедупликация корректна при любом порядке доставки).
- Набор тестов на соответствие протоколу (protocol conformance suite), общий для всех реализаций Core/SDK на разных языках — гарантирует, что независимые реализации ведут себя одинаково (Protocol Before Implementation).
- Core проектируется так, чтобы каждый его внутренний модуль можно было протестировать без поднятия сетевого стека целиком (Testability).
