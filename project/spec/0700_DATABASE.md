# 0700. База данных

## Статус
Черновик

## Назначение
Выбор и схема баз данных, используемых узлами инфраструктуры, за
интерфейсом Repository ([[0004_GLOSSARY]]) — ни один Service не обращается
к конкретной СУБД напрямую (Replaceability, Loose Coupling).

## Выбор СУБД
Референсный выбор: PostgreSQL для Node (Home Node, Storage
Node, Discovery Node) — зрелая, широко поддерживаемая реляционная СУБД с
хорошей поддержкой репликации; SQLite для локального хранилища Client
(см. [0400_CLIENT.md](0400_CLIENT.md)). Оба выбора заменяемы: доступ к
данным всегда проходит через Repository, поэтому смена СУБД требует
изменений только в реализации конкретного Repository (Replaceable
Everything).

## Схемы данных
Каждый тип Node владеет собственной изолированной схемой, не разделяемой
напрямую с другими типами узлов (Single Responsibility):
- **Home Node** — зарегистрированные Device и их публичные Identity-ключи, привязка UserID к активным устройствам.
- **Storage Node** — метаданные буферизованных Packet (получатель, TTL, отметка времени) и ссылка на зашифрованное тело; см. [0602_STORAGE_NODE.md](0602_STORAGE_NODE.md).
- **Discovery Node** — подписанные записи разрешения адресов и каталог Capability узлов; см. [0604_DISCOVERY_NODE.md](0604_DISCOVERY_NODE.md).

Ни одна из этих схем не содержит расшифрованное содержимое Message —
содержимое никогда не покидает E2EE-конверт на пути через инфраструктуру.

## Шифрование данных
Диск/том с базой данных шифруется как защита в глубину (см.
[0300_CRYPTO.md](0300_CRYPTO.md) → Шифрование хранимых данных), в
дополнение к тому, что хранимая полезная нагрузка уже является
E2EE-шифротекстом.

## Репликация и отказоустойчивость
Референс: primary-replica репликация для небольших развёртываний
(self-hosted Home Node), горизонтально шардированный кластер — для
крупных операторов инфраструктуры. Выбор конкретной топологии — решение
оператора конкретного узла, не требующее изменений в остальной сети
(Scalability).

## Миграции схемы
Миграции версионируются и применяются только вперёд (forward-only);
каждая миграция обязана сохранять обратную совместимость на время
скользящего обновления (rolling deployment), чтобы старые и новые версии
Service могли временно работать с одной и той же схемой (Backward
Compatibility).

## Резервное копирование
Бэкапы снимаются в зашифрованном виде; процедура восстановления
регулярно проверяется на тестовом окружении — бэкап, который ни разу не
был восстановлен, не считается надёжным.
