# 0005. Основа реализации: перенос лучшего из secure-messenger-project и secret_room; настоящий E2EE вместо временного

## Статус
Accepted

## Дата
2026-07-05

## Контекст
На диске обнаружены два прошлых незавершённых проекта того же продукта:
`~/secure-messenger-project` и `~/secret_room`. Оба содержат значительный
объём кода, но ни один не является цельным рабочим продуктом — типичный
результат AI-ассистированной разработки без единой спецификации (то, ради
чего написана вся текущая спецификация в `spec/`). Решено использовать
лучшее из обоих вместо разработки с нуля (см.
[ADR-0004](0004-mvp-staged-implementation.md), который эта запись частично
пересматривает).

## Что взято из каждого проекта

### Из `secret_room`
- **Схема данных backend** (`User`, `Device`, `Conversation`, `Message`, `PreKey`, `SignedPreKey`, `Receipt`) — почти дословно соответствует терминам [0004_GLOSSARY.md](../0004_GLOSSARY.md) (`Identity`, `Device`, `Conversation`, `Message`, prekey-инфраструктура из [0300_CRYPTO.md](../0300_CRYPTO.md)). Берётся как основа схемы Home Node.
- **Структура FastAPI-бэкенда** (роуты, async SQLAlchemy, WebSocket-эндпоинт) — как каркас Home Node.
- **TURN-конфиг и WebRTC-скелет звонков** (`turn/turnserver.conf`, `call_manager.dart`, web call API) — берётся как референс на будущем этапе проектирования звонков (см. пробел, отмеченный при аудите доков — звонки пока не специфицированы отдельным документом).
- Крипто-модуль на TypeScript (`web/src/crypto/*`, 953 строки, `@signalapp/libsignal-client`) — используется как **дизайн-референс** (модель PreKey/SignedPreKey/Session, порядок X3DH-хендшейка), а не переносится дословно, так как основной клиент — Flutter/Dart, а не веб/TS (см. решение по крипто ниже).

### Из `secure-messenger-project`
- **Идея федерации/мультиузловой маршрутизации**: `RoutingService`, `FederationService`, `NodeDiscoveryService`, схема `NODE_ID`/`PEERS`, docker-compose топологии (3nodes/federation) — адаптируется под нашу терминологию (Home Node/Relay Node/Discovery Node из [0600–0604](../0600_HOME_NODE.md)) и разносится по отдельным сервисам вместо одного и того же образа, поднятого трижды.

### Что не переносится
- Frontend на React (оба проекта) — наш клиент Flutter, см. требование пользователя.
- Admin-панели, USB-key/master-password флоу, метрики — вне текущего MVP-среза (базовые функции: чаты, группы, сообщения, медиа).
- Double Ratchet-заглушка из `secure-messenger-project` (нерабочая) и незавершённая интеграция крипто-модуля `secret_room` с бэкендом — заменяются полноценной реализацией (см. ниже), а не портируются как есть.

## Пересмотр языка backend из ADR-0004
ADR-0004 выбрал TypeScript/Node.js для Home Node, Storage Node и Discovery
Node. Поскольку код, переносимый из `secret_room` и
`secure-messenger-project`, уже написан на **Python/FastAPI** и содержит
рабочую структуру (async SQLAlchemy, роуты, WebSocket, сервисы
маршрутизации), продолжать на нём быстрее, чем переписывать на другой язык
ради единообразия. **Решение:** Home Node, Storage Node, Discovery Node —
**Python/FastAPI** вместо TypeScript. Правило «язык выбирается на сервис»
из ADR-0004 остаётся в силе — Relay Node и Media Node по-прежнему
проектируются как простые протокольные адаптеры, кандидаты на переписывание
на Rust при появлении реальной нагрузки.

## Пересмотр крипто-плана из ADR-0004
ADR-0004 допускал временный упрощённый Crypto Provider (NaCl `box`/`secretbox`
без полного X3DH/Double Ratchet) за стабильным Crypto API, чтобы не
блокировать первую рабочую версию. Проверка показала, что для Dart/Flutter
существует `libsignal_protocol_dart` — чистый Dart-порт Signal Protocol
(X3DH + Double Ratchet), работающий без FFI и потому совместимый с web-,
mobile- и desktop-таргетами Flutter из одной кодовой базы.

**Решение:** использовать `libsignal_protocol_dart` как реализацию Crypto
Provider **сразу**, минуя временную NaCl-схему из ADR-0004. Crypto API,
Identity/Device/Session/KeyStore модели и Message Envelope, описанные в
ADR-0004, остаются контрактом без изменений — меняется только внутренняя
реализация Crypto Provider (она и должна была быть заменяемой по этому же
ADR). Таким образом MVP получает полноценный, а не временный E2EE.

**Известный компромисс:** `libsignal_protocol_dart` распространяется под
GPL-3.0. Проект и так задуман как полностью открытый (см.
[0000_PROJECT.md](../0000_PROJECT.md), [0002_PRINCIPLES.md](../0002_PRINCIPLES.md) →
Open Standards), поэтому конфликта с текущими принципами нет; это стоит
учитывать только если в будущем возникнет необходимость закрытой/проприетарной
сборки — тогда потребуется отдельное решение (например, замена на
собственную интеграцию `libsignal-client` через FFI).

## Последствия
- Групповая E2EE-схема из [0301_GROUP_MESSAGING.md](../0301_GROUP_MESSAGING.md) (sender keys) реализуется поверх `libsignal_protocol_dart`'s group-примитивов либо вручную поверх его парных сессий — уточняется на этапе реализации групп.
- Backend (Home Node) в MVP не участвует в шифровании и не хранит приватные ключи ни при каком сценарии — только пересылает и буферизует шифротекст, что сохраняет инвариант Privacy First без исключений даже на этапе MVP.
- Федеративная маршрутизация переносится из `secure-messenger-project`, но протокол сообщений между узлами — наш собственный JSON Envelope (см. [0201_PACKETS.md](../0201_PACKETS.md) как целевой формат; JSON — временная сериализация до перехода на бинарный протокол, см. [ADR-0004](0004-mvp-staged-implementation.md)).
- Звонки (WebRTC) остаются вне первого среза; TURN/CallManager-код из `secret_room` сохраняется как референс для будущего документа спецификации звонков.
