# 0006. Поэтапная децентрализация: bootstrap-центр регистрации и мониторинга нод

## Статус
Accepted

## Дата
2026-07-05

## Контекст
[0002_PRINCIPLES.md](../0002_PRINCIPLES.md) → Decentralization First требует
отсутствия центрального управляющего Node. На практике, на текущей стадии
проекта (один разработчик/владелец, сеть только запускается) полностью
децентрализованная регистрация узлов с самого первого дня создаёт реальную
операционную проблему: невозможно проверить, какие ноды вообще существуют
в сети, какая версия ПО на них запущена, и не скомпрометирована ли она —
а значит, невозможно осмысленно развивать протокол и вовремя заметить
проблему у конкретного оператора узла.

Это тот же класс компромисса, что уже зафиксирован в
[0005_DESIGN_PHILOSOPHY.md](../0005_DESIGN_PHILOSOPHY.md) — сети со схожими
целями (Certificate Transparency, ранние фазы многих федеративных сетей)
типично проходят через bootstrap-стадию с одним или несколькими доверенными
узлами до того, как доверие может быть распределено.

## Решение
На текущей стадии проекта один Discovery Node назначается **корневым**
(root) — это операционное соглашение (какой URL ноды настроены
регистрироваться), а не новый программный механизм принуждения:
- Любая новая Node (Home/Relay/Storage/Media) при старте регистрируется в
  корневом Discovery Node через уже существующий `POST /registry/nodes`,
  дополнительно сообщая `software_version`.
- Корневой Discovery Node периодически получает heartbeat от каждой ноды
  (`POST /registry/nodes/{id}/heartbeat`) и вычисляет статус
  online/offline по давности последнего heartbeat.
- Результат виден человеку через простую read-only панель (Node Monitor,
  см. `project/admin/`) — «увидеть ноду как рабочую», как это было
  сформулировано в постановке задачи.

**Важное ограничение scope**: «проверка на компрометацию» на этом этапе
означает только сверку заявленной `software_version` — не криптографическую
удалённую аттестацию (remote attestation), не проверку хэша бинарника, не
подпись сборки. Полноценная аттестация — гораздо более тяжёлая задача с
собственной моделью угроз (кто подписывает «хорошие» версии, как
распространяется отзыв доверия) и сознательно вынесена в будущую работу.

Это **осознанное временное отступление** от Decentralization First, а не
пересмотр самого принципа — принцип остаётся целевым состоянием сети.

## Roadmap децентрализации этого механизма (не делается сейчас)
- Несколько Discovery Node с gossip-репликацией записей друг с другом — уже
  заложено как направление в [0604_DISCOVERY_NODE.md](../0604_DISCOVERY_NODE.md) → Отказоустойчивость и репликация.
- Переход от «доверия одному корню» к взаимной сертификации нод
  (web-of-trust: ноды подтверждают легитимность друг друга подписями,
  без обязательного единого корня).
- Возможность полностью выключить исходный корневой Discovery Node без
  остановки сети — то есть корень должен быть *первым bootstrap-узлом*,
  а не архитектурно обязательной точкой отказа.
- Более сильная проверка версии/компрометации (например, подписанные
  релизы, список отозванных версий, публикуемый не единолично).

## Последствия
- Discovery Node в этой версии — не просто справочник адресов, а активный
  реестр с состоянием (heartbeat, версия, online/offline) — расширяет его
  ответственность за пределы того, что было в [0604_DISCOVERY_NODE.md](../0604_DISCOVERY_NODE.md) исходно; документ обновлён соответствующим разделом.
- Каждый сервис (Home/Relay/Storage/Media Node) обязан регистрироваться и
  слать heartbeat корневому Discovery Node при старте — небольшая, но
  обязательная сетевая зависимость на этапе запуска (если корневой
  Discovery Node недоступен в момент старта, сама Node должна продолжать
  работать — регистрация best-effort, не блокирующая).
- Это решение подлежит пересмотру по мере роста сети — зафиксировано явно
  в Roadmap выше, а не оставлено как молчаливое отступление.

## Связь с Node Enrollment (ADR-0009)
ADR-0009 развивает bootstrap-центр ADR-0006 в полноценный Control Plane:
`trust_status`, выдача `node_token` после подтверждения оператором, режим
`ENROLLMENT_MODE=legacy` для обратной совместимости. Это не отменяет
roadmap децентрализации выше — enrollment — следующий шаг эволюции того
же корневого Discovery, а не замена его постоянным «master»-сервером.
