# 0007. Временный мост: вход по идентификатору (телефон/логин/email) + пароль

## Статус
Accepted

## Дата
2026-07-05

## Контекст
[0300_CRYPTO.md](../0300_CRYPTO.md) фиксирует аутентификацию через
challenge-response на Ed25519-ключе устройства, без паролей. Это верно для
входа с уже известного устройства, но не решает практический сценарий:
пользователь хочет зарегистрироваться по телефону/имени (и опционально
логину/email) и входить по любому из этих идентификаторов — в том числе
предположительно с нового устройства. Полноценное решение (привязка нового
устройства к существующей Identity через подпись существующего устройства)
пока не спроектировано.

## Решение
Временный мост, явно признанный небезопасным относительно целевой модели:
- Регистрация: `phone` (обязательно), `display_name` (обязательно),
  `login`/`email` (опционально), `password` (обязательно).
- Пароль хранится как `argon2id`-хэш (примитив уже в списке
  [0300_CRYPTO.md](../0300_CRYPTO.md) → Используемые примитивы — не вводим
  новый).
- Вход: `identifier` (телефон/логин/email) + `password` → JWT. Существующий
  Ed25519 challenge-response (`/auth/challenge` + `/auth/verify`) остаётся
  для конкретного устройства, но перестаёт быть единственным путём входа.
- Телефон/email на этом этапе **не верифицируются** (нет OTP/SMS/email
  confirmation) — указать чужой номер технически возможно. Осознанно принято
  как временное, по прямому указанию.

## Последствия
- Нарушает Zero Trust/Privacy First в части «пароли не используются» —
  зафиксировано явно, не молча.
- Roadmap: убрать пароль, когда появится привязка нового устройства к
  существующей Identity через подпись уже доверенного устройства (или
  восстановление по seed-фразе) — тогда `/auth/login` по паролю выводится из
  эксплуатации, а не остаётся навсегда.
- Схема БД Home Node меняется (`User` += `phone`, `login`, `email`,
  `password_hash`) — dev-база пересоздаётся.
