# 0008. Звонки: сигналинг поверх E2EE-канала сообщений, медиарелей — новый Turn Node

## Статус
Accepted

## Дата
2026-07-06

## Контекст
[ADR-0005](0005-reuse-legacy-projects-and-real-crypto.md) вывел звонки за
пределы первого среза и отметил, что они не специфицированы отдельным
документом. Экран «Звонки» в клиенте (`calls_screen.dart`) — полностью
моковый UI без какого-либо сигналинга и без WebRTC.

Сеть — federated: вызывающий и вызываемый могут обслуживаться разными
Home Node, между которыми доставка идёт напрямую либо через Relay Node
как fallback (см. [0100_ARCHITECTURE.md](../0100_ARCHITECTURE.md),
[0601_RELAY_NODE.md](../0601_RELAY_NODE.md)). Требовалось решение по двум
независимым вопросам:
1. Как сигналинг звонка (offer/answer/ICE) находит вызываемого через
   произвольное число промежуточных нод, не создавая новой
   инфраструктуры маршрутизации отдельно от уже существующей для
   сообщений.
2. Как передавать сами медиапотоки (SRTP), когда P2P между устройствами
   невозможен (NAT).

## Рассмотренные варианты

### Сигналинг
1. **Через существующий E2EE-канал сообщений** — сигнальные сообщения как
   control-содержимое (`call_offer`/`call_answer`/`call_ice_candidate`/...)
   внутри уже установленной попарной Session, доставляются как обычный
   Message. Плюсы: наследует уже работающую федерацию Home Node ↔ Home
   Node и Relay-fallback без единой новой строчки в маршрутизации;
   end-to-end зашифровано по умолчанию; тот же паттерн, что уже принят и
   проверен для распространения группового sender key
   ([0301_GROUP_MESSAGING.md](../0301_GROUP_MESSAGING.md)). Минусы: сигналинг
   разделяет задержку и семантику доставки обычных сообщений (не
   специализирован под real-time).
2. **Новые типы Packet на уровне протокола** (`CALL_OFFER`/`CALL_ANSWER`/...
   в [0201_PACKETS.md](../0201_PACKETS.md)). Плюсы: явная типизация на
   уровне протокола. Минусы: требует правок federation-кода на всех нодах
   и в Discovery для нового класса трафика — фактически дублирует то, что
   уже работает для Message.
3. **Отдельный signal-node сервис.** Плюсы: чистое разделение
   ответственности. Минусы: дублирует уже написанную и проверенную логику
   федерации/relay-fallback сообщений; больше кода и рисков для MVP без
   видимой выгоды по сравнению с вариантом 1.

### Медиарелей (TURN)
1. **Только STUN, P2P напрямую** (без TURN). Плюсы: ноль новой
   инфраструктуры. Минусы: звонок не устанавливается за симметричным
   NAT/строгим firewall — не решает задачу для реалистичной доли сетей.
2. **Новый Turn Node с self-registration в Discovery** (тот же паттерн,
   что и остальные ноды, [ADR-0006](0006-staged-decentralization-bootstrap-authority.md)).
   Плюсы: полноценный TURN-relay, консистентен с уже принятой моделью
   discovery/heartbeat; явное разделение ответственности (TURN работает с
   непрерывным медиапотоком реального времени, а не дискретными Packet).
   Минусы: новый тип узла, новый сервис для развёртывания и эксплуатации.
3. **Расширить Relay Node под TURN.** Плюсы: меньше новых сущностей.
   Минусы: Relay Node сейчас пересылает дискретные протокольные Packet и
   не хранит состояние дольше одной пересылки; TURN требует allocation
   state на весь звонок и работы с непрерывным UDP/RTP — смешение этих
   двух моделей в одном компоненте нарушает Single Responsibility
   ([[0003_ENGINEERING_PRINCIPLES]]) сильнее, чем выгода от переиспользования.

## Решение
- Сигналинг звонков — **вариант 1**: control-сообщения поверх
  существующего E2EE-канала (см. [0303_CALLS.md](../0303_CALLS.md) для
  полной схемы, подтипов и диаграммы). Новых типов Packet, нового
  сервиса или изменений в federation-коде для сигналинга не вводится.
- Медиарелей — **вариант 2**: новый тип узла **Turn Node** (см.
  [0605_TURN_NODE.md](../0605_TURN_NODE.md)), со своей регистрацией и
  heartbeat в Discovery Node по тому же паттерну, что Home/Relay/Storage/
  Media Node.

## Последствия
- [0101_COMPONENTS.md](../0101_COMPONENTS.md) дополнен строкой Turn Node в
  таблице узлов инфраструктуры.
- [0004_GLOSSARY.md](../0004_GLOSSARY.md) дополнен термином Turn Node.
- Реализация сигналинга — работа клиента (Core/Crypto Layer) и вызывающих
  экранов, backend-ноды не меняются вообще (сигналинг для них — opaque
  Message, как и любой другой). Это дешёвый первый шаг реализации.
- Turn Node — новый сервис для реализации и развёртывания; требует
  временных TURN-credential (см. [0605_TURN_NODE.md](../0605_TURN_NODE.md) →
  Ограничения) до эксплуатации вне тестового окружения — не блокирует
  первую работающую версию звонков в закрытом тестовом контуре (можно
  начать с публичного тестового STUN и локально поднятого coturn без
  credential-механизма, донастроить перед реальным использованием).
- Групповые звонки, multi-device fan-out, push для входящего звонка —
  явно вне текущего решения (см. [0303_CALLS.md](../0303_CALLS.md) → Не входит
  в MVP), отдельные будущие решения.
