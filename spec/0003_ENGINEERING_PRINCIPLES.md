# 0003. Engineering Principles

## Статус
Черновик

## Назначение документа
Данный документ определяет фундаментальные инженерные правила проекта.

Любой новый модуль, сервис, библиотека, API или пользовательский интерфейс
должны соответствовать данным принципам.

Если предлагаемое решение нарушает один или несколько принципов, решение
считается неверным независимо от его производительности, простоты
реализации или скорости разработки.

Этот документ не про бизнес — он про мышление разработчика. Он должен быть
прочитан (человеком или Cloud Code) прежде, чем будет написана хотя бы одна
строка кода. Продуктовые и сетевые принципы проекта см. в
[0002_PRINCIPLES.md](0002_PRINCIPLES.md).

## Принципы

### 1. Architecture Before Code
Код никогда не является отправной точкой.

Сначала определяется архитектура. После утверждения архитектуры создаются
интерфейсы. Только после этого начинается реализация.

Запрещается писать код, который впоследствии определяет архитектуру
проекта. Архитектура всегда имеет более высокий приоритет, чем реализация.

### 2. Specification First
Каждая новая возможность должна сначала быть описана в документации.

Документация является единственным источником истины. Код должен
соответствовать документации. Документация не должна переписываться под уже
существующий код.

### 3. Protocol Before Implementation
Любой сетевой механизм сначала проектируется как независимый протокол.

После этого могут существовать любые реализации: Flutter, Go, Rust, Python,
Java, C#, JavaScript. Все реализации обязаны вести себя одинаково.

См. [0200_PROTOCOL.md](0200_PROTOCOL.md).

### 4. Loose Coupling
Компоненты должны иметь минимальное количество зависимостей.

Изменение одного модуля не должно требовать изменения остальных модулей.
Все взаимодействия происходят через стабильные интерфейсы.

### 5. Replaceability
Любой компонент должен быть заменяемым.

Замена одной технологии не должна приводить к переписыванию системы. Не
допускается зависимость архитектуры от конкретного поставщика технологий.

### 6. Single Responsibility
Каждый модуль отвечает только за одну область ответственности. Например:

- Relay пересылает сообщения.
- Storage хранит данные.
- Media хранит файлы.
- Crypto выполняет криптографические операции.
- Client отображает интерфейс.

Ни один модуль не должен выполнять функции другого.

### 7. Offline First
Любая операция должна корректно работать без доступа к сети.

Пользовательский интерфейс не должен зависеть от текущего состояния
соединения. Все изменения сначала фиксируются локально. Синхронизация
происходит автоматически.

### 8. Event Driven
Система должна быть ориентирована на события.

Необходимо избегать тесной связи между компонентами. Компоненты должны
реагировать на события, а не постоянно опрашивать друг друга.

### 9. Stateless Communication
По возможности сетевые взаимодействия должны быть независимыми друг от
друга.

Серверы не должны хранить лишнее состояние. Минимизация состояния упрощает
масштабирование и повышает отказоустойчивость.

### 10. Privacy by Default
Любое решение должно минимизировать сбор данных.

Если компоненту не требуется определённая информация для выполнения своей
задачи, он не должен её получать. Сбор дополнительных данных запрещён.

### 11. Zero Trust
Ни один внешний компонент не считается доверенным.

Каждый пакет должен проходить проверку. Каждая подпись должна быть
проверена. Каждый Node рассматривается как потенциально недоверенный.
Доверие строится исключительно на криптографических механизмах и
спецификации протокола.

### 12. Security by Design
Безопасность не должна добавляться после разработки.

Каждый модуль обязан учитывать безопасность на этапе проектирования. Все
криптографические операции выполняются только специализированным модулем.
Самостоятельная реализация криптографических алгоритмов запрещена.
Используются только проверенные и общепринятые криптографические
примитивы.

См. [0300_CRYPTO.md](0300_CRYPTO.md).

### 13. Open Standards
По возможности используются открытые стандарты.

Закрытые технологии допускаются только при отсутствии открытых альтернатив.
Любая зависимость от внешнего поставщика должна иметь возможность замены.

### 14. API as Contract
API является контрактом между компонентами.

После публикации API изменение его поведения без новой версии запрещено.
Совместимость является обязательной.

См. [0800_API.md](0800_API.md).

### 15. Backward Compatibility
Каждая новая версия должна максимально сохранять совместимость.

Удаление существующего поведения допускается только после официального
процесса устаревания.

### 16. Simplicity
Если две архитектуры решают одну задачу одинаково хорошо, выбирается более
простая.

Сложность допускается только при наличии объективной необходимости.

### 17. Performance Through Design
Производительность должна достигаться за счёт архитектурных решений.

Недопустимо компенсировать плохую архитектуру более мощным оборудованием.

### 18. Observability
Каждый компонент должен предоставлять информацию о своём состоянии:

- логи;
- метрики;
- трассировка;
- диагностика.

Все эти механизмы должны быть встроены изначально.

### 19. Testability
Каждый модуль должен проектироваться таким образом, чтобы его можно было
протестировать независимо от остальных компонентов.

Если модуль невозможно протестировать отдельно, его архитектура требует
пересмотра.

### 20. Long-Term Thinking
Все архитектурные решения принимаются с расчётом на долгосрочное развитие
проекта.

При выборе между быстрым решением и архитектурно правильным решением
предпочтение всегда отдаётся архитектурно правильному. Проект должен
оставаться понятным и сопровождаемым спустя годы, независимо от смены
технологий, разработчиков и инструментов.

## Рекомендации для Cloud Code
При создании нового кода необходимо:

- сначала изучить соответствующую спецификацию;
- определить область ответственности нового компонента;
- использовать существующие интерфейсы;
- избегать дублирования логики;
- соблюдать модульность;
- не нарушать принципы данного документа;
- обновлять документацию одновременно с кодом.

Если реализация требует нарушения любого из принципов, необходимо сначала
предложить изменение спецификации проекта, а не изменять архитектуру
самостоятельно.
