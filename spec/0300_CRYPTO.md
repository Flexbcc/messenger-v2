# 0300. Криптография

## Статус
Черновик

## Назначение
Криптографическая схема сквозного шифрования, аутентификации и целостности
данных. Реализуется исключительно внутри Crypto Layer
([[0004_GLOSSARY]]) — ни один другой модуль не реализует криптографические
примитивы самостоятельно (Security by Design, Zero Trust,
[[0003_ENGINEERING_PRINCIPLES]]).

## Модель угроз
Протокол проектируется в предположении, что:
- сеть ненадёжна и может терять, дублировать или переупорядочивать пакеты;
- ни один промежуточный Node (Relay, Storage, Media, Discovery, чужая Home Node) не является доверенным и может логировать или анализировать всё, что через него проходит (Zero Trust);
- оператор инфраструктуры любого отдельного Node может быть недобросовестным или скомпрометированным;
- устройство пользователя (Device) считается доверенным, пока не скомпрометировано физически — защита от компрометации самого устройства (кейлоггеры, root/jailbreak-эксплойты) выходит за рамки протокола;
- метаданные (факт и время связи, размер сообщения) минимизируются, но не гарантированно полностью скрыты в первой версии протокола (см. [0203_ROUTING.md](0203_ROUTING.md) → приватность маршрутизации).

Полная модель угроз (активы, конкретные позиции атакующего и разбор по
каждому классу узла) вынесена в отдельный документ — см.
[0302_THREAT_MODEL.md](0302_THREAT_MODEL.md).

## Шифрование сообщений (E2EE)
Референсная схема — установление общего секрета через X3DH-подобный
handshake (обмен на базе долгосрочных identity-ключей, подписанных
prekey и одноразовых prekey) с последующим пошаговым обновлением ключей
сообщений по схеме двойного храповика (Double Ratchet). Это
общепризнанная, проверенная временем конструкция (Signal Protocol и его
производные) — проект не проектирует собственную схему E2EE (Security by
Design, [[0002_PRINCIPLES]] → Privacy First: «Проект не разрабатывает
собственные криптографические примитивы»).

Свойства, которые обязана обеспечивать схема:
- **Forward secrecy** — компрометация текущего ключа сообщения не раскрывает предыдущие сообщения.
- **Post-compromise security** — после компрометации сессия самовосстанавливается при следующем обмене ключами.
- **Аутентификация отправителя** — получатель может криптографически убедиться, что сообщение отправлено обладателем заявленной Identity.

Для групповых Conversation используется схема на основе sender keys
(каждый участник группы шифрует один раз для всех получателей собственным
ключом цепочки, обновляемым при изменении состава группы) — детальная
спецификация в [0301_GROUP_MESSAGING.md](0301_GROUP_MESSAGING.md).

## Управление ключами
- **Генерация ключей** — выполняется локально на Device, приватные ключи никогда не покидают устройство в открытом виде.
- **Хранение ключей на устройстве** — приватные ключи хранятся в защищённом хранилище платформы (Keychain/Keystore/эквивалент) либо в зашифрованной локальной БД, ключ шифрования которой производится из аппаратно защищённого секрета и/или пользовательского фактора разблокировки.
- **Верификация ключей** — пользователи могут сверить идентичность собеседника вручную через сравнение отпечатка ключей (safety number) или сканирование QR-кода, не полагаясь на доверие к инфраструктуре.
- **Ротация ключей** — подписанные prekey и одноразовые prekey периодически обновляются; долгосрочный identity-ключ может быть заменён только через явную процедуру привязки нового Device/переустановки, с уведомлением собеседников об изменении identity.
- **Отзыв ключей** — при компрометации или утере Device его identity-ключ отзывается через подписанную запись на Home Node/Discovery Node; все активные Session с этим Device считаются недействительными.

## Шифрование на уровне транспорта
Каждое сетевое соединение между двумя соседними узлами (Client↔Home Node,
Node↔Node) дополнительно защищается транспортным шифрованием (TLS 1.3 или
эквивалентное шифрование QUIC-рукопожатия, см.
[0103_NETWORK.md](0103_NETWORK.md)). Это защищает метаданные канала
(например, от пассивного перехвата на уровне сети) в дополнение к E2EE
полезной нагрузки, но не заменяет его — Node всегда получает только
зашифрованный E2EE-payload.

## Шифрование хранимых данных (at rest)
- **Storage Node** хранит исключительно E2EE-шифротекст Packet; у Storage Node нет ключа для его расшифровки (см. [0602_STORAGE_NODE.md](0602_STORAGE_NODE.md)).
- **Media Node** хранит файлы, зашифрованные на клиенте до загрузки; ключ файла передаётся получателю только внутри E2EE-конверта сообщения (см. [0603_MEDIA_NODE.md](0603_MEDIA_NODE.md)).
- **Локальная БД клиента** шифруется целиком ключом, производным от защищённого хранилища устройства (см. [0400_CLIENT.md](0400_CLIENT.md)).
- **База данных узлов** (метаданные Home/Discovery Node) шифруется на уровне диска/тома как защита в глубину; конфиденциальность содержимого сообщений при этом уже обеспечена E2EE независимо от этого слоя (см. [0700_DATABASE.md](0700_DATABASE.md)).

## Подписи и целостность пакетов
Каждый Packet подписывается отправляющим узлом (см. поле `signature` в
[0201_PACKETS.md](0201_PACKETS.md)). Каждый получатель на каждом хопе
обязан проверить подпись прежде, чем обработать или переслать Packet
дальше (Zero Trust: «каждая подпись должна быть проверена»).

## Используемые примитивы
Только проверенные, широко стандартизированные алгоритмы:
- **X25519** — согласование общего секрета (ECDH).
- **Ed25519** — цифровые подписи Identity и Packet.
- **AES-256-GCM** или **ChaCha20-Poly1305** — симметричное аутентифицированное шифрование (выбор конкретного шифра — параметр реализации/Capability, согласуемый при handshake).
- **Argon2id** — получение ключа из пользовательского фактора разблокировки локального хранилища.
- **SHA-256/BLAKE3** — хэширование (контентная адресация объектов в Media Node, дедупликация).

Ни один из перечисленных примитивов не разрабатывается проектом
самостоятельно — используются проверенные референсные реализации (Security
by Design).

## Аудит и известные ограничения
- Схема E2EE для групповых Conversation (см. [0301_GROUP_MESSAGING.md](0301_GROUP_MESSAGING.md)) требует отдельного независимого криптографического аудита перед стабилизацией.
- Протокол не скрывает метаданные факта и времени связи от Relay Node в первой версии (см. [0203_ROUTING.md](0203_ROUTING.md)).
- Компрометация самого Device выходит за пределы модели угроз протокола.
- Перед стабилизацией `MAJOR`-версии протокола обязателен независимый внешний аудит криптографической схемы; результаты фиксируются через ADR.
- Полный разбор угроз по компонентам — см. [0302_THREAT_MODEL.md](0302_THREAT_MODEL.md).
