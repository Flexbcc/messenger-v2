# 0002. Схема E2EE: X3DH + Double Ratchet вместо собственной криптографии

## Статус
Accepted

## Дата
2026-07-05

## Контекст
Проект не разрабатывает собственные криптографические примитивы (Privacy
First, [0002_PRINCIPLES.md](../0002_PRINCIPLES.md); Security by Design,
[0003_ENGINEERING_PRINCIPLES.md](../0003_ENGINEERING_PRINCIPLES.md)).
Нужна схема сквозного шифрования, обеспечивающая forward secrecy и
post-compromise security для сообщений между устройствами, включая
асинхронный обмен, когда получатель офлайн в момент отправки.

## Рассмотренные варианты
1. **Разработать собственную схему шифрования сессий** — отклонён сразу: прямо противоречит принципу «не изобретать собственную криптографию» и требует независимого аудита с нуля.
2. **X3DH (согласование ключей) + Double Ratchet (обновление ключей сообщений)** — общепризнанная, широко проаудированная конструкция (лежит в основе Signal Protocol и его производных), поддерживает асинхронную инициацию сессии без необходимости одновременного присутствия обеих сторон в сети.
3. **Статический общий ключ на Conversation без ratchet-обновления** — проще в реализации, но не даёт forward secrecy: компрометация ключа раскрывает всю историю переписки.

## Решение
Выбран вариант 2. Подробности зафиксированы в
[0300_CRYPTO.md](../0300_CRYPTO.md) → Шифрование сообщений (E2EE).
Групповые Conversation используют производную схему на основе sender
keys, которая специфицируется отдельно по мере проработки.

## Последствия
- Асинхронная доставка (получатель офлайн) поддерживается нативно за счёт prekey-механизма X3DH, что согласуется с Offline First.
- Требуется управление жизненным циклом identity-ключей, подписанных prekey и одноразовых prekey (см. [0300_CRYPTO.md](../0300_CRYPTO.md) → Управление ключами).
- Перед стабилизацией схемы для групповых Conversation обязателен независимый криптографический аудит.
