# 0004. Поэтапная реализация MVP: язык на сервис, временный Crypto Provider за стабильным Crypto API

## Статус
Accepted

## Дата
2026-07-05

## Контекст
[ADR-0003](0003-core-language-rust.md) зафиксировал Rust как референсный язык
Core, а [ADR-0002](0002-e2ee-scheme-x3dh-double-ratchet.md) — полный X3DH +
Double Ratchet как схему E2EE. Оба решения корректны для целевой
архитектуры, но их реализация с нуля откладывает появление первой рабочей
версии продукта на длительный срок — противоречит Simplicity и Long-Term
Thinking в той части, где они требуют не платить сложностью за то, что не
даёт немедленной ценности (см.
[0003_ENGINEERING_PRINCIPLES.md](../0003_ENGINEERING_PRINCIPLES.md)).

Одновременно Privacy First — принцип, который прямо запрещено нарушать ради
скорости разработки (см. [0002_PRINCIPLES.md](../0002_PRINCIPLES.md) и
раздел «Рекомендации для Cloud Code» в
[0003_ENGINEERING_PRINCIPLES.md](../0003_ENGINEERING_PRINCIPLES.md)): любое
решение, ослабляющее «сервер никогда не видит содержимое сообщения»,
недопустимо даже для MVP.

## Решение

### 1. Язык выбирается на сервис, а не на всю платформу
Protocol Before Framework уже гарантирует, что язык реализации — деталь,
не влияющая на совместимость (см. [ADR-0001](0001-protocol-first-architecture.md)).
Поэтому для MVP:
- **Home Node, Storage Node, Discovery Node** — TypeScript (Node.js). Это в основном CRUD и realtime-фан-аут поверх WebSocket, где скорость итерации важнее сырой производительности.
- **Relay Node, Media Node** — реализуются в MVP тоже на TypeScript, но проектируются как чистые протокольные адаптеры (принять Packet → определить следующий хоп → переслать; принять blob → сохранить/отдать по ссылке) без бизнес-логики внутри. Это осознанно оставляет им простой контракт, чтобы позже переписать именно эти два узла на Rust (единственные узлы на «горячем пути» с высокой нагрузкой) без изменений на стороне Client, Home Node или Discovery Node.
- **Crypto Layer** — не сетевой сервис, а библиотека за стабильным Crypto API (см. ниже), встроенная в Client и, где нужно, в Node. Язык реализации Crypto Provider меняется независимо от API.

### 2. Crypto API фиксируется сейчас; Crypto Provider — временный
Проектируется финальный контракт (не меняется при переходе на полный
Signal-подобный стек):
- **Crypto API** — методы `generateIdentity()`, `generateDevice()`, `encryptForConversation(conversationId, plaintext)`, `decryptEnvelope(envelope)`, `rotateKeys()`, `verifySignature()`.
- **Identity Model** — долгосрочный keypair пользователя, не привязан к устройству или Home Node.
- **Device Model** — keypair устройства + привязка к Identity.
- **Session Model** — состояние текущего защищённого канала между двумя Device (в MVP — установленный общий секрет; в финальной версии — состояние Double Ratchet).
- **Key Store** — интерфейс хранения приватных ключей на устройстве, не зависящий от того, что именно хранится (одна пара ключей сейчас, полное дерево ratchet-состояний позже).
- **Message Envelope** — формат зашифрованного тела Packet с явным полем версии крипто-схемы (`crypto_version`), чтобы получатель знал, каким Crypto Provider расшифровывать.

Ни один компонент вне Crypto Layer (Client UI, бизнес-логика, любой Node)
не обращается к криптографической библиотеке напрямую — только через
Crypto API (Single Responsibility, Zero Trust).

### 3. Временная реализация Crypto Provider для MVP
- Основано на проверенной библиотеке (NaCl/libsodium: `box` для парного согласования ключа, `secretbox` для симметричного шифрования сообщений) — не собственная криптография (Security by Design).
- Парный X25519 `box` между двумя Device устанавливает общий симметричный ключ Conversation (упрощённый аналог сессии из X3DH, без prekey-инфраструктуры и без ratchet-обновления на каждое сообщение).
- Групповая Conversation использует тот же принцип, что и финальная схема из [0301_GROUP_MESSAGING.md](../0301_GROUP_MESSAGING.md): один симметричный ключ группы, распространяемый каждому участнику через парный `box` — структурно совместимо с sender-key подходом, просто без ротации при каждом сообщении.
- Сервер (любой Node) при этой схеме физически не может расшифровать `payload` — инвариант Privacy First сохраняется, даже несмотря на упрощение.

### 4. Явно не реализуется в MVP
X3DH с prekey-бандлами, Double Ratchet, MLS, post-compromise security за
счёт автоматического ratchet-обновления, сложная ротация ключей,
резервное восстановление ключей. Это переносится на отдельный этап после
первой рабочей версии и не является нарушением спецификации — это
временная реализация за постоянным контрактом (см. `crypto_version` в
Message Envelope).

## Последствия
- Замена временного Crypto Provider на полный Signal-подобный стек в будущем требует изменений только внутри Crypto Layer — Client UI, Home Node, формат Packet верхнего уровня и транспорт не переписываются.
- Relay Node и Media Node в MVP не оптимизированы по производительности — это осознанно, они не на критическом пути до появления реальной нагрузки.
- Групповая Conversation в MVP не имеет forward secrecy на уровне ротации при выходе участника (см. [0301_GROUP_MESSAGING.md](../0301_GROUP_MESSAGING.md) → Удаление участника) — это временно и должно быть закрыто до продакшен-релиза с реальными пользователями, не только до внутренней демонстрации.
- Перед любым продакшен-использованием обязателен переход на полную схему из [0300_CRYPTO.md](../0300_CRYPTO.md)/[0301_GROUP_MESSAGING.md](../0301_GROUP_MESSAGING.md) и аудит (см. [0302_THREAT_MODEL.md](../0302_THREAT_MODEL.md)).
